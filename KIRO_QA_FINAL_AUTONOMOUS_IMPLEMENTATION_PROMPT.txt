1. ANSWERS TO YOUR PHASE A CLARIFICATIONS
======================================================================

A. STAGING / BRANCH TEST EXECUTION

Normal QA execution targets staging environments and branch environments.

These environments are intended for testing.

Full E2E flows in staging/branch environments may perform the normal test actions required by the existing suite, including test booking flows, when those actions are part of the intended QA behavior of those environments.

Do not reinterpret staging as production.

Do not unnecessarily block legitimate staging/branch test execution merely because a flow creates test data.

However:

- preserve test-data discipline;
- avoid uncontrolled duplicate data where practical;
- preserve cleanup where the system supports it;
- do not assume staging data is disposable if the repository indicates otherwise;
- do not extend test execution to production as part of ordinary validation.

B. PRODUCTION SAFETY GUARD

The repository already contains a deliberate production safety mechanism, currently represented by `support/productionGuard.ts`.

Its purpose is important and intentional.

When the configured baseURL is exactly the real production URL, the guard requires three confirmation questions before test execution is allowed.

Execution attempts are also recorded by the existing mechanism.

For staging and other non-production URLs, the guard intentionally does not behave like the production gate.

PRESERVE THIS SAFETY MODEL.

You may improve the implementation only if necessary and only if all of the following remain true:

1. production remains explicitly distinguishable from staging/branch environments;
2. accidental production execution remains guarded;
3. the three-confirmation safety behavior is not silently weakened;
4. no bypass is introduced;
5. production execution never becomes the default;
6. production safeguards are covered by deterministic validation where practical;
7. production credentials or sensitive data are never exposed.

Do not remove the production guard.

Do not simplify it in a way that weakens protection.

C. `--disable-web-security`

The current use of `--disable-web-security` is intentional for staging/branch testing.

Staging may contain incomplete integrations, cross-origin behavior, temporary environment constraints, or other conditions that are not representative of production.

Therefore:

DO NOT classify `--disable-web-security` as automatically incorrect merely because it weakens browser security boundaries.

DO NOT remove it globally without evidence.

Instead:

- preserve it where staging/branch testing actually requires it;
- scope it as narrowly as reasonably possible;
- determine whether every Playwright project needs it or only specific staging-oriented projects;
- do not generalize it to production;
- do not weaken production browser/security behavior;
- if it can safely be removed from a subset of projects without breaking legitimate staging tests, you may narrow its scope;
- validate any change before keeping it.

This is a deliberate QA-environment exception, not authorization to weaken production security.

D. PLAYWRIGHT MCP UNSAFE EXECUTION

Your audit identified broad auto-approval involving `browser_run_code_unsafe`.

Treat this separately from `--disable-web-security`.

They are not the same issue.

Review the existing MCP configuration against Kiro Enterprise policy and least privilege.

Prefer not to auto-approve arbitrary JavaScript execution when deterministic or safer Playwright tools are sufficient.

You are authorized to tighten auto-approval if doing so does not break required QA workflows.

Do not expand MCP permissions.
